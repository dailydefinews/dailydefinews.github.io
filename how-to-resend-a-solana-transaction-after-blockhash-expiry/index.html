How to Resend a Solana Transaction After Blockhash Expiry

Solana transaction failed with “blockhash not found”? Fetch a fresh blockhash, re-sign, and resend before lastValidBlockHeight; match commitment across RPC calls.

Onchain Report NewsroomNov 28, 2026 · 04:49 UTC#68a6733 min read

After a Solana transaction fails with “blockhash not found,” fetch a fresh blockhash, re-sign and resend before its lastValidBlockHeight; use the same commitment level and RPC node for fetching and preflight.

Why Solana says “blockhash not found” and how to fix it

A Solana transaction usually has an expired or unknown recent blockhash. Validators accept only blockhashes they know from roughly the last 150 blocks, or about a minute. Once that window passes, the signed transaction cannot land.

The most common cause is slow signing. A hardware wallet approval or wallet prompt left open can outlast the blockhash window. The transaction may be ready to sign, but by the time you approve it, the recent blockhash has expired. Fetch a fresh one, rebuild and re-sign the transaction, then send it again.

Use getLatestBlockhash to get both a recent blockhash and its lastValidBlockHeight: the last block height at which the transaction can land. Rebroadcast the signed transaction while the current block height is still at or below that value. After it passes, stop resending that transaction and sign a new one with a fresh blockhash.

A commitment mismatch is another common cause, even when the blockhash looks fresh. A node can return a blockhash at processed commitment before another node has seen that block. If preflight simulates the transaction on the slower node, it may report “blockhash not found.” Fetch the blockhash and run preflight at the same commitment; using the same RPC node for both also avoids differences in what each node has seen. confirmed is a practical choice: fetch there, re-sign, then rebroadcast while the block height remains valid.

A USDC bridge claim on Solana can fail for the same timing reason. Its attestation remains valid until redeemed, so the claim can simply be submitted again with a fresh transaction. The separate task of bridging USDC from Ethereum to Solana concerns moving crypto between chains; the claim here is a Solana transaction step.

An expired transaction is never executed, so it charges no fee and changes no state. If a fresh, correctly signed transaction still fails after you align commitment and RPC node, contact the wallet or RPC provider with the transaction signature, error, blockhash commitment and RPC endpoint. That gives them details to investigate.

Related questions

What does “block height exceeded” mean on Solana?

It means the current block height passed the transaction’s lastValidBlockHeight. The recent blockhash expired, so sign a new transaction with a fresh one.

When should a durable nonce replace a recent blockhash?

Use a durable nonce when signing may take longer than the recent-blockhash window, such as a workflow that waits for a hardware wallet or offline signer. A durable nonce lets the transaction use a stored nonce instead of a short-lived recent blockhash.

More Solana transaction questions

How do I set preflightCommitment in web3.js?

Set the connection’s preflightCommitment to the same commitment used when fetching the blockhash, such as confirmed. Keep the RPC node consistent too.

Why do some RPC providers return this error more often?

RPC nodes can be at different points in the chain. A node that has not seen the blockhash returned by another node may reject it during preflight.

Can a transaction with an old blockhash still land later?

No. Once its last valid block height passes, validators will not accept that transaction. Create and sign a new one with a fresh blockhash.
